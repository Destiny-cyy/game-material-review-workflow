# ad-material-review 详细说明文档

> 面向：渠道发行 / 投放 / 素材运营同学，以及要接手这套流程的人。
> 目标：不写代码也能看懂「这套东西解决什么问题、怎么用、换游戏改哪里、坑在哪」。
> 本文件用大白话讲，配图；技术细节放在 `SKILL.md`、`config/config.schema.md` 和脚本注释里。

---

## 一、这套东西到底解决什么问题（先看这个）

想象你要回答老板/项目组这几个问题：

- 我们投了这么多素材图，**哪种画风更吸引人**？
- 画面上**放不放福利、怎么放福利**有没有用？
- **老用户 / 新用户**分别吃哪一套？
- 一张图**反复投**会不会越投越没效果？
- 跟平台上其他游戏比，我们**到底算好还是差**？
- 下个月要**新做多少张图**、优先做什么方向？

难点在于：投放后台给你的只有「曝光、点击、CTR」这些数字，它**不会告诉你这张图画的是什么**。
所以你没法直接回答「哪种画风 CTR 高」——因为「画风」这个信息根本不在数据里。

**这套工作流做的事**，就是补上这一环：

```
把「素材长什么样」→ 变成一张张图的结构化标签 → 跟投放数字拼在一起 → 算出哪种最好 → 指导下个月做什么
```

用一张图表示整条链：

```
┌─────────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│ 1.投放明细   │   │ 2.素材图片    │   │ 3.逐张看图    │   │ 4.合并 + 分析 │   │ 5.结论/报告  │
│ 曝光/点击/   │ + │ 按链接去重    │ → │ 打视觉标签    │ → │ 标签×CTR 归因 │ → │ 缺口/排期/   │
│ 分层/日期    │   │ 下载唯一图    │   │ (画风/元素/福利)│  │ 大盘对比/衰减 │   │ 行动建议      │
└─────────────┘   └──────────────┘   └──────────────┘   └──────────────┘   └──────────────┘
   只读原表           AI 多模态看图       结构化字段          曝光加权算 CTR       可分享产物
```

一句话价值：**把「设计感觉」变成「可对比的数字」，让下个月做素材有依据，而不是拍脑袋。**

## 二、它在整条业务链上处在哪个位置

对新手补个背景（老手可跳过）：

```
选游戏/定档期 → 定投放资源位 → 【做素材】 → 投放 → 看数据 → 【复盘归因】 → 下一轮做素材
                                    ▲                          ▲
                              channel-resource-table        ★本 skill★
                              （要做什么、什么规格、什么时候交）  （做过的哪类好、下轮做什么）
```

- 前一个环节（资源需求表）管的是「向前看：这次要收哪些素材、什么规格、什么时候交」。
- 本 skill 管的是「向后看：历史素材哪类有效」，把结论喂给下一轮素材生产。
- 两者一前一后，形成闭环。

## 三、几个必须先分清的概念（最容易混）

| 概念 | 大白话 | 为什么重要 |
|---|---|---|
| **投放记录** | 后台里的一行 = 一次投放（某天、某人群、某个位置投了某张图） | 一张图会被投很多次，所以记录很多 |
| **唯一创意图** | 按图片链接去重后的「张数」 | 打标是按「张」打的，不是按「行」打的 |
| **CTR** | 点击率 = 点击 ÷ 曝光 | 但**必须曝光加权**，不能把每行 CTR 平均 |
| **曝光加权** | 把一组的所有点击加起来 ÷ 所有曝光加起来 | 一条大曝光素材和小曝光素材对整体贡献不同，简单平均会被小样本噪声带偏 |
| **用户分层** | 后台的人群定向（纯新/老用户/兴趣标签等） | 不同人群效率差很多，混在一起看会误判 |
| **大盘 Benchmark** | 拿平台上其他游戏当参照系 | 光看自己涨跌不够，得知道「相对别人算什么水平」 |
| **复用衰减** | 同一张图反复投，效率会不会掉 | 决定「该补新图」还是「继续吃老本」 |

> **最常犯的错**：把「M 条投放记录」当成「M 张图」。实际往往 M 条记录只对应 N 张图（N 明显小于 M）。每次交付都要主动写清用的是哪个口径，别等对方问。

### 两个 CTR 口径，结论可能相反（重要）

```
游戏级（曝光加权）：把整个游戏所有投放合起来算 → 看「大盘位置」，容易被爆款和档期拉高
素材级（单张中位）：每张图各算 CTR，取中位数   → 看「素材平均水准」，不受曝光量影响
```

一个很典型的情况：**游戏级看着很好（进了前 X%），但素材级中位只在中下游**。
这说明整体好看是靠几张爆款 + 某个大档期撑着，**真正的瓶颈是素材平均水准偏弱**。
所以两个口径都必须算，只看一个会误判。

## 四、完整流程（七阶段，配图）

```
阶段1 摸底取数  →  阶段2 定标签体系  →  阶段3 逐张看图打标  →  阶段4 写入打标子表
                                                                        ↓
阶段7 缺口测算/排期  ←  阶段6 出报告/文档  ←  阶段5 效果分析（含大盘对比/复用衰减）
```

**阶段 1 · 摸底取数**
先别急着拉全量，先 `GROUP BY` 看清数据覆盖几个月、目标游戏有多少条、有没有名字变体。
然后 `fetch_materials.py` 拉明细生成主表，并按图片链接去重下载唯一图。原表只读。

**阶段 2 · 定标签体系**
这是全链路最需要「人」判断的一步。三到四类标签：
- **画风**（单选，互斥）：写实渲染 / 概念原画 / 平面插画 / UI 展示 / 实机截图……
- **画面元素**（多选，最多 3 个）：单角色 / 多角色 / 战斗 / BOSS / 场景 / 大字文案 / 奖励物……
- **福利呈现**（单选）：堆叠式 / 独立圈圈式 / 单品聚焦 / 大字福利文案 / 无福利
- **节点、用户分层、置信度**：由配置或原表带出

四条标准：**互斥穷尽、只看画面就能判、设计师看得懂能执行、别拆太细否则样本不够**。
详细判定标准见 `references/tag-taxonomy.md`；两套示例预设在 `config/presets/`。

**阶段 3 · 逐张看图打标**
把唯一图分成几批，交给 AI **逐张打开图片看**（不是读标题猜！），输出每个标签。
把握不准的标「中」置信度进人工复核清单。主会话抽查几张校验质量。
然后 `label_merge.py` 把标签按「图→记录」回填（一张图被投多次，所有记录都带上同一组标签）。

**阶段 4 · 写入打标子表**
`write_smarttable.py` 新建一张子表存打标结果（原表不动），字段选项从配置生成。

**阶段 5 · 效果分析**
`analyze.py` 出各维度 CTR，`benchmark.py` 出大盘双口径，`reuse_map.py` 出复用衰减明细。

**阶段 6 · 出报告**
HTML 报告模板 + 可选在线文档。报告写什么、不写什么由 `report.narrative` 控制（见第六节）。

**阶段 7 · 缺口测算**
```
月需求 = 投放天数 × 每天要几张差异化图
可复用 = 现有素材里历史验证有效、能延展的底稿数
净缺口 = 月需求 − 可复用
```
必须写明三条假设（每天几张、老图复用率、是否含版本换新缓冲），并给优先级和「暂缓」清单。

## 五、换一款游戏要改什么（可迁移的核心）

**这是本包最关键的设计**：所有游戏专属的东西只在 `config/config.json` 一份文件里。

```
┌────────────────────────────────────────────────────┐
│                 config/config.json                 │
│  游戏名 · 平台 · 子表名 · 字段名 · 标签体系 ·        │
│  节点档期 · 对标游戏 · 图片域名 · 叙事策略           │
└───────────────────────┬────────────────────────────┘
                        │ 读取
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
   取数脚本         分析脚本         报告模板
   （都不写死      （都不写死      （纯占位符）
    游戏信息）      游戏信息）
```

迁移三步：
1. `cp config/config.example.json config/config.json`
2. 按 `config/config.schema.md` 逐项填真实值（约 10 分钟）
3. 用 `examples/` 的假数据空跑一遍，确认配置读得到，再接真实数据源

**逐项清单**（完整版见包根《迁移到新游戏指南.md》）：

| 改哪里 | 换成什么 |
|---|---|
| `project` | 游戏名、平台、数据区间 |
| `source` | docid、子表名、`mode`（自有台账 / 大盘表） |
| `fields` | 源表真实列名对照 |
| `taxonomy` | 该游戏的标签体系（或复制一份 preset 改） |
| `nodes` | 档期日期（**要向业务确认**） |
| `benchmark` | 游戏名变体 `aliases`、对标游戏 `peers` |
| `output` | 图片 CDN 域名、Referer |
| `report.narrative` | 与业务方确认报告能写什么 |

## 六、报告叙事：一个容易忽略的「业务规矩」

不同业务方对「报告能不能写排名、垫底」要求不一样，所以做成**开关**而不是写死：

| `report.narrative` | 报告里写什么 | 适用 |
|---|---|---|
| `neutral` | 客观全量展示 | 内部复盘、给自己看 |
| `positive_only` | 只写**有优势的、环比进步的**；「垫底/末位/分位/排名」不进报告 | 给更上层看的汇报 |
| `full` | 全量含排名分位 | 明确要求完整披露时 |

**`positive_only` 的三条要点**：
1. 优先用「**改了什么 → 好了多少**」的对照叙事（例如「X 月起全面加福利，CTR 环比提升」），而不是排名羞辱。
2. 任何与对标游戏的对比**必须同时给曝光量**——只给点击率不给分母是误导。某个维度没优势就删掉该对比，宁可少写。
3. 扎心数据（排名、分位、与头部差距）**不进报告，但必须算出来留档**，并在交付时口头/私信告知业务方本人。叫「不隐瞒，但不写进给更上层看的报告」。

> 用 `neutral` 也建议先看一眼 `references/analysis-playbook.md` 的「对外脱敏对照」：曝光与金额用**量级/倍数**，CTR 用**倍数/百分比差异/排名**，不写绝对值。

## 七、最容易踩的坑（都踩过）

| 坑 | 后果 | 怎么避 |
|---|---|---|
| 游戏名有变体 | 大盘表同一游戏两三个名字，不合并会算出 CTR≈0 的假结果 | `benchmark.aliases` 收齐，先 `GROUP BY 游戏名` 看全部变体 |
| 大盘表月份覆盖不全 | 只有近几个月，却拿去比全年 | 报告对比区间按大盘表实际范围写 |
| 只看游戏级口径 | 误判「整体挺好」 | 游戏级 + 素材级都算 |
| 简单平均 CTR | 小曝光素材噪声主导结论 | 一律曝光加权 |
| 同链接多条记录回填错 | 打标大面积为空 | 映射保留**首次出现**的 rowid |
| 多选字段用等值分组 | 一条记录只算进一个元素组 | 用「包含」口径，并说明组间重叠 |
| 图片读图缓存 | 第二次读同一张图看不到内容 | 复制文件 + JPEG 头插 COM 段绕过 |
| 命令行超长 | 一次写几百条报 `WinError 206` | 分批写（默认 50 条/批） |
| 文档留旧版 | 业务方看到的是旧结论 | 替换而非叠加，见 `doc-sync.md` |
| 对外产物带本地路径 | 分享出去别人打不开 | 只放 CDN 网址 |

完整坑表见 `references/table-ops.md` 和包根《避坑指南.md》。

ad-material-review/

## 九、三分钟上手（不接真实数据也能跑）

从**包根目录**（能看到 `README.md` 和 `examples/` 的那一层）执行：

```bash
python skills/ad-material-review/scripts/analyze.py \
  --config examples/config.demo.json \
  --csv examples/tagged.sample.csv \
  --out examples/out/analysis.json
```

`examples/` 里全是**编的假数据**，可安全外发。跑通说明配置和脚本都正常，再按第五节换上真实数据。

## 十、这份包是脱敏通用版，注意两点

1. 包内**不含任何真实游戏名、平台名、真实 CTR/曝光数字、内部文档 ID、人名**。示例数据全是编的，图片域名是 `cdn.example.com` 占位。
2. 正式使用前请把 `config.json` 里的占位值换成真实值，并把 `output.cdn_base` 换成你们平台的图片域名；**不要把真实业务数据写回脚本或提交到公开仓库**。
