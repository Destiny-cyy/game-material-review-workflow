# 交付 DDL 怎么排（通用方法）

> 本文件讲**方法和因果逻辑**，所有平台名、天数、锚点均为占位示例，按你们平台官方文档替换。

## 🔴 第一原则：先分「活动/直播前」还是「活动/直播后」

**凡是需要从活动/直播本身派生出来的素材（切片 / 录播 / 精彩剪辑 / 合集），
因果上只能在活动结束之后才存在，DDL 必须挂在 T 之后，不是 T 之前。**

真实教训（已抽象）：第一版把视频素材和合集全排在 T-7（活动前），
用户当场纠正——「视频合集是得在活动结束后做成切片视频，才能有视频素材」。
这不是排期松紧问题，是**因果顺序错误**，排得再漂亮也是假的。

判断方法：问一句「**这个东西在活动开始前，理论上能不能存在？**」
答不能 → 挂 T 之后。

## 通用锚点（占位，按你们平台规则替换）

设 T = 上架 / 开播 / 活动日。

### T 之前（倒推）

| 环节 | 提前量 | 依据 |
|---|---|---|
| 平台直播流邮件报备 | 无明文天数、非即开即用 → 越早越好，标「★最早启动」 | 规则 X.X |
| 入库确认 | 配置前 N 周；未入库需申请，流程约 N 天 | 规则 X.X |
| 非常态位报备 | 需运营评定协商排期 → 约 T-N | 规则 X.X |
| 视觉定制素材 | **申请通过后**才需要，留评审/返工时间 → 约 T-N | 规则 X.X |

关键点：定制视觉不是「报备时就交」，而是**申请通过后才开始做**。
报备和交素材之间必须留出评审时间，否则会出现「刚报备就要交图」这种没时间做的排法。

### T 之后（顺推）

| 环节 | 时间 | 说明 |
|---|---|---|
| 切片源文件 / 封面 / 标题 / 作者信息 | T+N 左右 | 活动结束后切片制作约 N 天 |
| 站外链接 | 切片交付后 +N 天 | 须**先在外站发布**才有链接；上架前 N 天给链接审核 |
| 合集标题 / 封面 / Icon / 清单 | 再往后约 N 周 | 须视频**先逐个上架**才可整理成合集 |

## 日历层面的硬约束（按平台实际改）

- 某些上架动作**暂不支持周末 / 节假日** → 相关动作必须落在**工作日**
- 另一些动作（如上下架定时）可能**支持含周末** → 别和前者混为一谈
- 报备评审类动作优先排工作日，避开周五下午和周末
- 凡是「运营要评定 / 协商排期」的环节，不要卡着下限排，留 buffer

## 排完后必做的两项自检

1. **因果自检**：把每项按 DDL 排序，看有没有出现「东西还没产生就要交」的情况。
   （例如合集排在切片之前 ×）
2. **门槛自检**：有量化门槛的位置（如合集要求 ≥N 篇、单篇播放 ≥N），
   确认按这个 DDL 交付时门槛能不能达到。达不到要把「实际排期会被推迟」这件事告诉用户，
   不要假装表上的日期就是上架日。

## 呈现方式

DDL 列**只写结论日期**；若确有必要加一个 ★ 优先级标记，仅允许这一种附加文字。
「为什么是这天」在对话里告诉用户，不写进表（见 `content-principles.md` 第八条）。
给出理由是为了让填表的人知道哪个不能拖——尤其「★最早启动」那项，
它是整条链的瓶颈，晚一天后面全顺延。
