# channel-resource-table 详细说明文档

> 面向：渠道发行 / 市场 / 项目协作同学。不写代码也能看懂。
> 本文件用大白话讲「这套东西干嘛、两张表什么区别、怎么用、坑在哪」。

---

## 一、它解决什么问题（先看这个）

你要在某个平台申请一批资源位（比如商店 banner、直播专区、热搜位），
需要品牌方 / 市场团队给你一堆素材：主视觉图、文案、切片视频、封面、Icon……

难点不是「做表」，而是：
- 平台规则文档又长又碎，**哪些位能申请、要什么规格、要不要提前报备**，没人一次性讲清楚；
- 直接把规则文档甩给合作方，对方看不懂也不知道该干嘛；
- 交付时间排错（比如把「直播切片」排在直播之前），整张表就是假的。

**这套工作流做的事**：把「平台规则」翻译成**两张表**——

```
                    ┌──────────────────────────┐
   平台规则文档  →   │ ① 全景表（给自己看）      │  内部推演：有哪些位/什么规则/够不够格/进度
   （又长又碎）      │ ② 需求表（发给合作方）    │  对外收东西：要什么/什么规格/什么时候给
                    └──────────────────────────┘
                         ▲ 两张表必须成对，口径一致
```

一句话价值：**内部有一本明白账，对外有一张能直接填的表。**

## 二、在业务链上的位置

```
选游戏/定档期 → 【定资源位 + 收素材】 → 投放 → 复盘归因 → 下一轮
                      ▲                        ▲
              ★本 skill★                 ad-material-review
              （向前看：这次要做什么）      （向后看：做过的哪类好）
```

本 skill 管「向前看」，素材复盘 skill 管「向后看」，一前一后形成闭环。

---

## 三、两张表到底什么区别（最容易混）

| | ① 全景表 | ② 资源/素材需求表 |
|---|---|---|
| 给谁 | 自己 / 渠道侧内部 | 品牌方 / 市场 / 合作方 |
| 回答 | 有哪些位？什么规则？够格吗？对接人？进度？ | 要什么？什么规格？什么时候给？往哪填？ |
| 内容 | 重：规则出处、名额、审核红线、资格判定、报备进度 | 轻：只有素材项、规格、DDL、交付内容空列 |
| 能不能外发 | **不能**（太重，对方看不懂） | 能 |

**铁律**：不要把全景表直接发给合作方。两张表口径必须一致，改一处同步另一处。

## 四、动手前先定五件事（决定表的行列）

1. **平台与专区**：哪个平台的哪个专区（不同专区规则完全不同，别串）
2. **可用资源位清单**：按规则文档列全，标常态 / 非常态
3. **本次申请范围**：通常**只申请非常态位**——常态位多为系统自动拉取，申请了没用
4. **申请资格**：逐条套规则，判定走哪条通道；资格不成立的表做了白做
5. **素材项**：每个位要几样东西，逐项拆开

> 规则文档有两份以上时，先分清各自管什么（例如一份管「专区」、一份管「商店位」），**两套体系别混**。

---

## 五、内容取舍：写什么、不写什么

**精简表只写三件事：要什么 · 什么规格 · 怎么交付**
- 素材三件套拆成三列：素材说明（要什么内容）／规格要求（尺寸格式大小）／关键规范要求（易踩坑的硬条件）
- 备注列只放对接人、链接、模板提示
- **不写**：规则背景、名额限制、审核红线、资格判定、报备进度、规则背后的「为什么」
- 留一列空的「交付内容」给对方填

> 真实教训（已抽象）：写过一版带全部规则背景的表，被判「太体系化、内容太多」；
> 删干净又被判「太简单」，补回模板链接和关键规范才合适。
> **平衡点：保留交付标准（尺寸/格式/硬条件），删掉推导过程。**

### ★ 单元格只填结论，不填理由（最容易犯）
```
✗ X月X日（周X）｜须提前 N 天报备      ← 有理由
✗ X/X                                  ← 斜杠格式
✓ X月X日                              ← 正确
✓ X月X日 ★ 最早启动                   ← 唯一可加的：优先级标记
```
为什么选这天、依据哪条规则——**在对话里告诉用户，不要写进表**。
星期几也不用写（用户自己会看日历）。

## 六、排交付 DDL：一个因果顺序的坑

**第一原则：先分「活动/直播前」还是「活动/直播后」**

```
问一句：这个东西在活动开始前，理论上能不能存在？
答「不能」 → DDL 必须挂在 T 之后（顺推）
答「能」   → 挂在 T 之前（倒推）
```

**从活动本身派生出来的素材**（切片 / 录播 / 精彩剪辑 / 合集），因果上只能在活动结束后才存在。
把这些排在 T 之前不是「排期紧不紧」的问题，是**因果顺序错误**，排得再漂亮也是假的。

```
T 之前（倒推）：报备 → 入库确认 → 资格评定 → 定制视觉（申请通过后才开始做）
        T = 上架/开播日
T 之后（顺推）：切片源文件 → 外站链接 → 合集（须视频先逐个上架）
```

排完做两项自检：
1. **因果自检**：按 DDL 排序，看有没有「东西还没产生就要交」
2. **门槛自检**：有量化门槛的位置，确认按这个 DDL 交付时门槛能不能达到；达不到要如实告诉用户

日历硬约束（示例，按你们平台实际改）：某些上架动作可能不支持周末/节假日，
报备评审类优先排工作日。详细锚点见 `references/ddl-planning.md`。

## 七、角色称谓先确认，别猜

「品牌方 / 合作方 / 渠道方 / 平台方」这几个词**先问清楚指谁再动手**。
典型业务模型：

```
品牌方（自家品牌/市场团队）策划并出素材
        ↓
渠道侧（我方）收齐
        ↓
投到平台（各内容/商店载体）做宣传
```

> 真实教训（已抽象）：曾把某个「投放载体」当成了「品牌方」，整张表方向做反。宁可多问一句。

**对外表不刻意区分「我方」和「对方」**——都是一起的，表格是协作工具，不是划责任的清单。

## 八、表格怎么生成（技术部分，可略读）

- **不要走本地文件导入**（会被安全策略拦截），用在线接口新建空表再写入
- `scripts/table_sheet.py` 封装了建表/写数据/合并/样式/边框/尺寸/验收
- `scripts/build_sheet.py` 读一个 JSON spec 一键生成整张表
- 执行顺序固定：写数据 → 合并 → 表格样式 → 字体 → 边框 → 尺寸 → 验收
- **接口返回成功 ≠ 验收通过**，五项断言全过才能报完成（见 `references/table-structure.md`）

`config/spec.example.json` 是一份填好的示例 spec，改改就能试。

## 九、最容易踩的坑

| 坑 | 后果 | 怎么避 |
|---|---|---|
| 把全景表发给合作方 | 对方看不懂 | 只发精简表 |
| 单元格写理由/星期 | 表变重、被手动清掉 | 只填结论 |
| 派生素材排在 T 之前 | 因果错误，整表作废 | 先分 T 前/T 后 |
| 把规则举例当排他 | 误排除可用通道 | 举例非排他，无依据标「需运营评定」 |
| 漏流程性门槛 | 报备/入库没预留，申请卡住 | 核查时重点找遗漏，不是找错误 |
| 擅自改用户定稿的表 | 返工、信任受损 | 核完报问题，由用户决定 |
| 两张表口径不一致 | 核对反复返工 | 改一处同步另一处 |
| 本地文件导入 | 被安全策略拦截 | 在线新建 + 脚本写入 |

完整坑表见 `references/table-cli-gotchas.md`、`references/rule-check.md`。

## 十一、脱敏说明

本包**不含任何具体平台规则、真实游戏名、真实资源位、真实对接人、真实日期**。
示例里的平台、专区、规则章节号、DDL 都是占位。
正式使用前请读你们自己的平台官方文档，把规则、规格、门槛、对接入口逐项填进 spec 与表里。
