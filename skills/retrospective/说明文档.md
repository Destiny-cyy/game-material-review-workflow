# retrospective 详细说明文档

> 面向：任何要做「复盘 / 整理 / 总结」的人。不写代码也能看懂。
> 这是三个 skill 里最轻的一个——它不产出表格或报告，而是**规定「做复盘这件事该怎么推进」**。

---

## 一、它解决什么问题

「复盘 / 整理 / 总结」这类任务最容易翻车的地方，不是不会写，而是：

- **各写各的**：这轮和上次说的口径对不上，结论自相矛盾；
- **数字来路不明**：写了个结论，问「哪来的」答不上，或者凭记忆复述越说越偏；
- **凑篇幅**：硬塞一堆没信息量的内容，把真正有用的淹了；
- **闷头通读**：一上来就把几十份资料全读一遍，时间花光了还没抓到重点；
- **手一抖删错东西**：把还该留的归档信息删了。

**这套流程做的事**：给它一套「弹性框架」——先判断这次该跑多重，再按需选动作，
但有三条底线无论如何不能破。

---

## 二、一句话理解「弹性」

```
固定死的（3 条底线）        可裁剪的（一堆动作）
┌────────────────┐      ┌──────────────────────────────┐
│ 1 先对齐       │      │ 对齐口径 / 选最优路径 /       │
│ 2 每步留痕     │  +   │ 清理内容 / 整合资料 /         │
│ 3 删前先问     │      │ 分头推进 / 归档收口           │
└────────────────┘      └──────────────────────────────┘
                              ▲ 按任务大小挑着用，不强制顺序
```

**它不是检查表，是判断框架**。资料少、任务小，压缩成一两轮也行，但三条底线不省。

---

## 三、三条底线（唯一写死的地方）

### 1. 先对齐
动手前把**以前定过的结论、记录、口径**摆出来对一遍，确认这轮和以前说的是同一件事、同一套说法。
对不上的先标出来，别闷头各写各的。

> 为什么：复盘最怕「这次说 A，上次说 B，两份都留着」，业务方看到的就乱了。

### 2. 每步留痕
每条结论、每个数字都能**追回出处**：来自哪份资料、怎么取的、有没有加工过。
加工过的保留中间产物，**不覆盖、不凭记忆复述**。

### 3. 删前先问
反复核实确认某条归档信息确实无用后，**先列出要删的、向用户确认**，同意了再删；
实体文件一律不直接删，只进回收站。

> 为什么：归档信息看着没用，可能是别人还在用的锚点。删错不可逆。

---

## 四、开始前先判断（决定这轮跑多重）

不套固定档位，按现场情况问自己四个问题：

| 问自己 | 决定什么 |
|---|---|
| 任务规模、资料量多大？ | 跑几轮、要不要建完整「资料地图」 |
| 有没有已有结论/口径要先对齐？对不上的多不多？ | 先处理冲突再往下 |
| 有没有能拆开并行处理的块？ | 要不要派多个子任务分头做（允许、非必须） |
| 范围清楚吗？ | 不清楚**先问**，别默认「全都要」 |

---

## 五、可裁剪动作（挑着用）

| 动作 | 干什么 | 关键点 |
|---|---|---|
| **对齐既有口径** | 逐条比对，标冲突 | 先处理冲突再往下 |
| **总结经验 + 选最优路径** | 不只写「发生了什么」，还要给「下次走哪条路最省事最稳」的一条明确推荐，并说明别的路为什么不划算 | 严格**区分事实 / 推测 / 主观判断**，分别标注 |
| **清理内容（两类都剔）** | 剔掉自相矛盾的、剔掉凑篇幅没信息量的 | 只留能对齐、有出处的；剔了什么**在留痕里记一笔**，不悄悄抹 |
| **整合资料（不通读）** | 不要通读 → 先建地图（只登记元信息）→ 按需取用 → 每步留痕 | 见下节 |
| **归档收口** | 定稿后归档 | 无用的按「删前先问」处理 |
| **分头推进与合稿** | 大任务派多个子任务并行 | **合稿前必须先互相对齐**，每块产出都带出处 |
| **收口后进下一段** | 上一段收口就自动进下一段，不停下来等确认 | 例外：要删东西、范围明显说不清 → 先问 |

---

## 六、「不通读」为什么重要（整合一批资料的规矩）

```
❌ 错误：把 30 份资料全读一遍 → 时间花光、抓不住重点
✅ 正确：
   ① 先建地图   只登记「有哪些资料、各自讲什么、在哪」，不读正文
   ② 按需取用   要回答哪个问题，才去读哪几份的对应部分
   ③ 每步留痕   读了哪份、取了哪条、怎么加工的，都记下来
```

这条规矩在游戏素材复盘、渠道资源表这两个 skill 里也都在用——**它是跨项目通用的工作习惯**。

---

## 七、一个容易忽略的坑：分头做完不合稿

大任务派了几个子任务并行，各自写各自的，最容易**口径对不上**：
同一个指标，A 用「唯一图」口径、B 用「投放记录」口径，结论一对就打架。

所以规矩是：**合稿前必须先互相对齐再收口**，每块产出都要带出处。
并行是为了快，不是为了省掉对齐这一步。

---

## 八、与其他规矩的关系

- 全局的「文件删除规则」「不修改原表」「对外先审后传」等红线**照常生效**，与本技能叠加、不互相覆盖。
- 「删前先问」与全局删除规则一致，**不得因为「阶段自动推进」就绕过**。
- 阶段自动推进 ≠ 可以跳过对齐，也不等于可以自作主张删东西。
- 用户明确说「不走流程 / 直接改」→ 尊重用户，跳过本框架。
